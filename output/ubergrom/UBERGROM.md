# p‑System cartridge — UberGROM package

These three files contain the same cartridge as `output/bin/` (`romcart.bin` plus
the console GROM images), laid out for UberGROM hardware: a 512K paged cart ROM
and an ATmega1284 UberGROM. They are generated by `build/make_ubergrom.py`.

| File | Size | Goes to |
|------|------|---------|
| `PCODE_ROM_8.BIN` | 512 KB | Cartridge ROM flash (paged `>6000‑7FFF`) |
| `PCODE_AVR_FLASH.BIN` | 128 KB | UberGROM AVR program flash |
| `PCODE_AVR_EEPROM.BIN` | 4 KB | UberGROM AVR EEPROM (configuration) |

## PCODE_ROM_8.BIN

`romcart.bin` unchanged. It is already exactly 512K, so it needs no padding. There
are 64 banks of 8K, and writing to `>6000+2n` selects bank n.

| Banks | Contents |
|-------|----------|
| 0 | DSR code C |
| 1 | DSR code D |
| 2 | Boot loader and RAM helpers |
| 3 | Stubs |
| 4‑48 | ROM disk `#12 PSYS:` |
| 49‑63 | Copies of bank 3 |

## PCODE_AVR_FLASH.BIN

The UberGROM firmware reads GROM page n from flash offset `n × >2000`.

| Flash offset | GROM page | Contents |
|--------------|-----------|----------|
| `>00000‑>09FFF` | 0‑4 | `grom_base0_base1.bin`, console GROM `>6000‑FFFF` |
| `>0A000‑>0F7FF` | 5‑7 | `grom_base2.bin`, console GROM `>6000‑B7FF` |
| `>0F800‑>1DFFF` | — | `>FF` padding (to 120K) |
| `>1E000‑>1FFFF` | — | `UberGROM_Program.bin` (8K AVR program) |

Page 7 holds only the last 6K of the base 2 image. Its final 2K (console
`>B800‑BFFF`, a GROM gap) is `>FF`.

## PCODE_AVR_EEPROM.BIN

The firmware (`main.c`) reads the configuration as follows:

* Flags are at `>000`, with their inverse at `>001`.
* With bases enabled, the map byte for (base, slot) is at `>002 + base·16 + slot`,
  where slot = GROM address ÷ `>2000`.
* Each map byte's inverse is stored 8 bytes later. If the two don't match, the slot
  is unmapped.
* A map byte is `(device << 4) | page`. Device 1 is GROM and device 6 is the flash
  controller.

Everything else in the file is `>00`. A `>00` byte with a `>00` inverse is
invalid, so those slots are unmapped, the same as in the example.

**Flags:** `>01` / `>FE`. This is the same as the example:
* GROM bases enabled.
* Recovery program still enabled (hold SPACE at power‑up).
* Rollover off, so addresses wrap within each 8K slot like real GROMs. The p‑code
  skips the GROM gaps itself.

**Slot map:**

| Base (ports) | `>6000` | `>8000` | `>A000` | `>C000` | `>E000` |
|---|---|---|---|---|---|
| 0 (`>9800`) | GROM p0 `>10` | p1 `>11` | p2 `>12` | p3 `>13` | p4 `>14` |
| 1 (`>9804`) | GROM p0 `>10` | p1 `>11` | p2 `>12` | p3 `>13` | p4 `>14` |
| 2 (`>9808`) | GROM p5 `>15` | p6 `>16` | p7 `>17` | — | — |
| 15 (`>983C`) | — | — | — | — | Flash ctrl `>60` |

Raw bytes:

```
>000: 01 FE                                   flags / inverse
>002: 00 00 00 10 11 12 13 14  00 00 00 EF EE ED EC EB   base 0
>012: 00 00 00 10 11 12 13 14  00 00 00 EF EE ED EC EB   base 1
>022: 00 00 00 15 16 17 00 00  00 00 00 EA E9 E8 00 00   base 2
>0F9: 60   >101: 9F                           base 15 >E000 = flash controller
```

The `00/00` pairs (the console slots `>0000‑>5FFF`, which the firmware ignores
anyway, and the unused base 2 slots) are invalid, so those slots are unmapped.

* Bases 0 and 1 map the same pages. The cart needs this (see `output/bin/LOAD.md`),
  and it also keeps the console from showing REVIEW MODULE LIBRARY.
* Base 15 `>F800‑FFFF` is always the configuration EEPROM, whatever the map says.
  The flash controller sits at `>E000` on that base, as in the example.

## Notes / differences from the example

* **Flash controller inverse:** the example (`SSA_AVR_EEPROM.bin`) puts `>60` at
  `>0F9` but leaves its inverse at `>101` as `>00`. Going by the firmware source,
  that makes the example's flash mapping *inactive*. Here the inverse is set to
  `>9F`, so the flash controller **is** active. That lets a loader reflash the GROM
  through base 15. If you want to match the example exactly (flash locked), set
  byte `>101` to `>00`.
* The example also contains its own user data at `>200‑>23F` and a `>60` at
  `>FF9`. These are outside the map area. They were not copied.
* **Recovery program:** on the first power‑up, the UberGROM briefly serves its own
  power‑up link at base 0 `>E000`. It drops it after the console has read the link
  at `>E00C/D`, so the p‑code GROM at `>E000` is visible from then on. Holding SPACE
  at power‑up replaces base 0/1 `>6000` with the recovery loader. To disable
  recovery for a production cart, set the flags to `>03` / `>FC`.
* A real console GROM still has to be present, because the UberGROM does not
  return address reads. The console GROMs provide that.
