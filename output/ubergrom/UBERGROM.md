# p‑System cartridge — UberGROM package

These three files contain the same cartridge as `output/bin/` (`romcart.bin` plus
the console GROM images), laid out for UberGROM hardware: a 512K paged cart ROM
and an ATmega1284 UberGROM. They are generated by `build/make_ubergrom.py`.

| File | Size | Goes to |
|------|------|---------|
| `PCODE_ROM_8.BIN` | 512 KB | Cartridge ROM flash (paged `>6000‑7FFF`) |
| `PCODE_AVR_FLASH.BIN` | 128 KB | UberGROM AVR program flash |
| `PCODE_AVR_EEPROM.BIN` | 4 KB | UberGROM AVR EEPROM (configuration) |

## PCODE_ROM_8.BIN

`romcart.bin` unchanged. It is already exactly 512K, so it needs no padding. There
are 64 banks of 8K, and writing to `>6000+2n` selects bank n.

No bank has a cartridge header: byte 0 of every bank is `>00` (the build asserts that
no bank starts with `>AA`). The console finds the cart through the boot GROM instead
(base 0 `>6000`, below). The boot entry is unchanged: select bank 2 (`CLR @>6004`) and
`B @>6100` (the loader).

| Banks | Contents |
|-------|----------|
| 0 | DSR code C |
| 1 | DSR code D |
| 2 | Boot loader (`>6100`), RAM helpers (`>6118`), 80‑column loader LOAD80 (`>6800`) |
| 3 | Stubs + GRAM code pool routines at `>6100` (`gram.s`) |
| 4‑48 | ROM disk `#12 PSYS:` |
| 49‑63 | Copies of bank 3 |

## PCODE_AVR_FLASH.BIN

The UberGROM firmware reads GROM page n from flash offset `n × >2000`.

| Flash offset | GROM page | Contents |
|--------------|-----------|----------|
| `>00000‑>01FFF` | 0 | Boot header GROM (base 0/1 `>6000`), also written to `build/bootgrom.bin` |
| `>02000‑>09FFF` | 1‑4 | p‑code GROM `>0000‑7FFF` (base 0 `>8000‑FFFF`) |
| `>0A000‑>11FFF` | 5‑8 | p‑code GROM `>8000‑F7FF` (base 2 `>6000‑D7FF`) |
| `>12000‑>1DFFF` | — | `>FF` padding (to 120K) |
| `>1E000‑>1FFFF` | — | `UberGROM_Program.bin` (8K AVR program) |

Page 8 holds only 6K of p‑code GROM. Its final 2K (console `>D800‑DFFF`, a GROM gap)
is `>FF`.

The RAM helpers (`XLAT` and its copies in `build/ramhelp.s`) translate a p‑code GROM
address P to the console: P < `>8000` is base 0 at P + `>8000`, otherwise base 2 at
P − `>2000`. The p‑System never addresses base 0/1 `>6000‑7FFF`.

### Boot header GROM (page 0, base 0/1 `>6000`)

Two programs. The console lists them in reverse order, so the first record is menu item 3.

| Menu | Record | GPL stub | ROM entry (bank 2) |
|---|---|---|---|
| 3 `UCSD P-SYSTEM (80 COL)` | `>600C` | `>6039` | `>6800` LOAD80 |
| 2 `UCSD P-SYSTEM` | `>6027` | `>604B` | `>6100` loader (40 columns) |

* Each GPL stub does `ALL >20` ; `DST >8302,@>8300` ; `DST >6004,@>8304` ;
  `DST entry,@>8308` ; `BR >605D` (twice, because BR resets COND).
* The common tail at `>605D` does `DST >04E0,@>8302` ; `DST >0460,@>8306` ; `XML >F0` ;
  `EXIT` ; `RTN`.
* `XML >F0` runs `CLR @>6004 ; B @entry` from scratchpad `>8302`.
* Generated by `boot_header()` in `build/make_ubergrom.py`.

### Screen (both entries)

* The VDP screen image table is at `>1000` (R2 = `>04`), part of the VDP freed by the
  GRAM code pool. The patched sites:
  * VDPCOP2 R2 (GROM `>EF2E`);
  * CURWIN `li r9` (`>47EA`);
  * SCRECHO `ai r5` (`>546E`);
  * PRSKEYX `li r4` (`>5BCC`).
* RESCON loads WIDTH from the RAM word `BOOTW` (`>3A02`, in the RAM helpers) instead of
  a literal 40. RESCON runs at startup and again from the OS's console UNITCLEAR.
* **80 columns:** LOAD80 copies the RAM helpers, sets `BOOTW` = 80, and then writes the
  VDP registers in this order:
  * R8–R15 = `08 00 00 00 00 00 00 00` (on a 9918A or a locked F18A these writes land
    in R0–R7);
  * R0–R7 = `04 F0 04 2F 00 18 00 17`.

  RESCON only rewrites R1–R7, so R0 = `>04` (80 columns) stays set. There is no VDP
  detection, so the 80‑column entry needs an F18A or a V9938/58.

## PCODE_AVR_EEPROM.BIN

The firmware (`main.c`) reads the configuration as follows:

* Flags are at `>000`, with their inverse at `>001`.
* With bases enabled, the map byte for (base, slot) is at `>002 + base·16 + slot`,
  where slot = GROM address ÷ `>2000`.
* Each map byte's inverse is stored 8 bytes later. If the two don't match, the slot
  is unmapped.
* A map byte is `(device << 4) | page`. Device 1 is GROM and device 6 is the flash
  controller.

Everything else in the file is `>00`. A `>00` byte with a `>00` inverse is
invalid, so those slots are unmapped, the same as in the example.

**Flags:** `>05` / `>FA`. The example has `>01`; this adds rollover:
* GROM bases enabled.
* Recovery program still enabled (hold SPACE at power‑up).
* Rollover on. The code pool in GRAM is one 15K block, so the p‑code fetch has to run
  straight from `>7FFF` to `>8000`. The p‑System never reads the GROM address back,
  so it doesn't matter that the UberGROM's address then differs from the console
  GROMs'. The p‑code GROM on bases 0‑2 always sets the address again at each chip
  step, so rollover doesn't affect it.

**Slot map:**

| Base (ports) | `>6000` | `>8000` | `>A000` | `>C000` | `>E000` |
|---|---|---|---|---|---|
| 0 (`>9800`) | Boot GROM p0 `>10` | p1 `>11` | p2 `>12` | p3 `>13` | p4 `>14` |
| 1 (`>9804`) | Boot GROM p0 `>10` | p1 `>11` | p2 `>12` | p3 `>13` | p4 `>14` |
| 2 (`>9808`) | GROM p5 `>15` | p6 `>16` | p7 `>17` | p8 `>18` | — |
| 3 (`>980C`) | GRAM RAM p0 `>00` | GRAM RAM p1 `>01` | — | — | — |
| 15 (`>983C`) | — | — | — | — | Flash ctrl `>60` |

Raw bytes:

```
>000: 05 FA                                   flags / inverse
>002: 00 00 00 10 11 12 13 14  00 00 00 EF EE ED EC EB   base 0
>012: 00 00 00 10 11 12 13 14  00 00 00 EF EE ED EC EB   base 1
>022: 00 00 00 15 16 17 18 00  00 00 00 EA E9 E8 E7 00   base 2
>032: 00 00 00 00 01 00 00 00  00 00 00 FF FE 00 00 00   base 3 (GRAM)
>0F9: 60   >101: 9F                           base 15 >E000 = flash controller
```

The `00/00` pairs (the console slots `>0000‑>5FFF`, which the firmware ignores
anyway, and the unused base 2 slot) are invalid, so those slots are unmapped.

* Base 3 is the 15K GRAM (UberGROM RAM, device 0). See "GRAM" below.
* Bases 0 and 1 map the same pages. The cart needs this (see `output/bin/LOAD.md`),
  and it also keeps the console from showing REVIEW MODULE LIBRARY.
* Base 15 `>F800‑FFFF` is always the configuration EEPROM, whatever the map says.
  The flash controller sits at `>E000` on that base, as in the example.

## GRAM (base 3)

The UberGROM's 15K of RAM is mapped on base 3, the first base the cartridge doesn't use.
It reads and writes like GRAM through the base 3 ports.

| Port | Use |
|------|-----|
| `>980C` | read data |
| `>9C0C` | write data |
| `>9C0E` | write address (high byte, then low byte) |

| GROM address (base 3) | Device | Size |
|---|---|---|
| `>6000‑>7FFF` | RAM page 0 | 8K |
| `>8000‑>9BFF` | RAM page 1 | 7K |
| `>9C00‑>9FFF` | RAM page 1, past the end | reads aren't driven, writes are dropped |

* The RAM is cleared at power‑up. AVR `.bss` is zero‑initialised, and nothing is kept
  across a power cycle.
* Rollover is on (flag `>04`), so `>7FFF` is followed by `>8000`, and the 15K
  runs as one block.
* The emulator or device must support rollover. A Classic99 build without
  rollover support breaks segment loads (for example "Segment EDITCORE not found").

### The p‑System code pool lives here

The primary code pool, which used to be in VDP RAM, is now all of the GRAM. The
p‑System still thinks it is VDP: segments keep code type `R15 = -1`, and the pool
uses "fake VDP" addresses.

| | Old (VDP) | Now (GRAM) |
|---|---|---|
| `INTMEM` (RAM `>2780`) | `>0DF8` | `>4000` |
| `TOPMEM` (RAM `>2782`) | `>3E3C` | `>7BFE` |
| Pool size | about 12K | about 15K |
| Code read port (`CODREAD[2]`, `R13`) | `>8800` | `>980C` |

* **Mapping:** fake address V is stored at GRAM `V + >2000` on base 3. Real VDP
  buffer addresses are always below `>4000`, so any address of `>4000` or more is in
  the pool.
* **VDP freed:** VDP `>0DF8‑>3E3B` is no longer used. Only the startup VDP‑size
  probe touches it.
* **Where the code is:**
  * Hot paths are RAM helpers in `build/ramhelp.s` (`LOADAD1`/`GETDAT`/`GETDAT2`,
    `ADDRCOP`'s `VDP1`, the BIOS sector copy `VDPMOV`, and the ROM‑disk driver).
  * The segment compactor and the real‑constant write‑back are in cart bank 3
    (`build/gram.s`).

## Notes / differences from the example

* **Flash controller inverse:** the example (`SSA_AVR_EEPROM.bin`) puts `>60` at
  `>0F9` but leaves its inverse at `>101` as `>00`. Going by the firmware source,
  that makes the example's flash mapping *inactive*. Here the inverse is set to
  `>9F`, so the flash controller **is** active. That lets a loader reflash the GROM
  through base 15. If you want to match the example exactly (flash locked), set
  byte `>101` to `>00`.
* The example also contains its own user data at `>200‑>23F` and a `>60` at
  `>FF9`. These are outside the map area. They were not copied.
* **Recovery program:** on the first power‑up, the UberGROM briefly serves its own
  power‑up link at base 0 `>E000`. It drops it after the console has read the link
  at `>E00C/D`, so the p‑code GROM at `>E000` is visible from then on. Holding SPACE
  at power‑up replaces base 0/1 `>6000` (the boot header GROM) with the recovery
  loader, so the p‑System entries are not listed in that case. To disable
  recovery for a production cart, set the flags to `>03` / `>FC`.
* A real console GROM still has to be present, because the UberGROM does not
  return address reads. The console GROMs provide that.
