some separate notes

pCode emulation:
- custom GROM access address with 64k of GROM available (really 0xF800, so 62k, but that's cause
  of the normal 6k GROM padding).
    - does NOT use the normal GROM access, so no conflict with the console GROMs
    - rpcodebyte, wpcodebyte
    - 0x5bfc = Read GROM DATA
    - 0x5bfe = Read GROM Address
    - 0x5ffc = Write GROM DATA
    - 0x5ffe = Write GROM Address
    - only if DSR ROM is active, and only those explicit addresses (odd is ignored)

- CRU at >1F00
    - bit 0x00 enables/disables the DSR at >4000
    - bit 0x80 does a bank switch (nDSRBank[0xf]), bit '1' to bank 2, bit '0' to bank 1
    - There is a full 16k of DSR ROM data. In standard TI format the first 4k is the same, but this is simpler.

- In theory, the GROMs are used in such a way that it would be possible to just make them
  work on multiple bases. This would take additional ROM code to track bases but would then work anywhere...
  Otherwise, we need some extra hardware.

- The AVR is too slow to do the decode in software. PI might be fast enough. ;)

- otherwise we need decode like so:

1bfc-1bff   1 1x11 1111 11xx
1ffc-1fff   1 1x11 1111 11xx - 10 bits ANDed

74LS133 is a 13-input NAND gate, this would work.
Since the AVR uses software to select, we don't care if it's AND or NAND.. but for the ROM chip to work, we need the opposite... 


So, to make an Ubergrom cart work with this:
- relocate the DSR ROM to run at >6000
- necessary to add a cartridge header, it won't autostart
- find the CRU bank switching, and convert to ROM writes (CRU not available on all consoles)
- move the four GROM access ports (probably only 3) to cartridge space
- Ubergrom modified to support all 64k, including address read back

- this might be a good PI zero project. We could fit the ROM and GROM onboard and let it serve everything.

On the idea that GROM data is only copied, and never executed.

So, setting the address is a minimum of 6 code bytes, and could be replaced with a single MOV if we can find a safe address to store it at.

    ie: mov r4,@>FFFE

Fetching a byte of data (safest to continue by byte, though words where possible might be faster) is always at least a register and offset, so 4 bytes. But we need to fetch the address, fetch FROM the address, and increment, which is much more... 10 bytes minimum

    ie: mov @>FFFE,r4
        movb *r4+,R0
        mov r4,@>fffe

When there's a word access, it can be smaller. But otherwise we're going to need to branch. It might not always be safe to BL (r11 might be in use). I suppose we could use specific branches for each function.

Unsurprisingly, the ROM is pretty full. it does have a proper header (needed for the autostart anyway). There's 20. bytes free in the C bank and almost 48 in the D bank. 4 bytes is enough for the absolute B @>xxxx.

I think the custom PI cart with the ROM and GROM emulation is the best way to do it.
